# 开发任务文档规范

将已知目标转为可执行、可追踪的开发任务，并保留需求、实现与验收之间的证据链。本 skill 可移植到其他仓库；路径、技术栈和检查命令不绑定当前项目。

## 参考文件

路径相对本 skill 目录，移植时携带整个目录：

- 新建任务集的默认结构和模板：`references/task-set-template.md`。
- 状态流转、完成度与验证记录：`references/maintenance-and-verification.md`。
- 场景测试：`evals/evals.json`。

## 1. 识别范围和现有约定

1. 明确用户希望新建、更新、整理还是仅审阅任务文档，确认目标仓库及允许修改范围。没有获得实现授权时，不修改业务代码或执行实际开发任务。
2. 读取适用的项目指令、现有任务索引和相关任务集；检查 Git 状态，保留用户未提交的工作。寻找用户指定的需求、设计、计划、决策、代码和测试，仅在任务范围内调查。
3. 确认现有任务路径、编号、状态、复选框、统计和验收约定。用户明确指定优先，其次是适用的项目规则及既有规范，最后才使用本 skill 的默认模板；不得违反更高优先级的限制。
4. 区分已确认需求、现有实现、历史证据、用户确认、推断和未知事项。找到现有任务的权威归属，避免重复维护同一任务状态。需求资料不存在时，可依据用户目标形成草案并标记假设和待确认项，不强制创建 PRD。
5. 目标或产品边界不清且影响任务拆分、验收或安全时先询问；可以安全推进的部分先整理。产品需求、技术方案或架构决策需变更时，先征求必要确认并更新对应上游文档，再调整任务；若无授权，记录冲突和阻塞，不自行扩大范围。

## 2. 创建或更新任务

- 在无既有约定时，默认创建 `docs/tasks/README.md` 和 `docs/tasks/<编号-名称>/{tasks,progress,verification}.md`；使用未占用的编号，必要时建立索引。用户或项目另有路径时沿用该路径，不为使用模板而迁移原目录。
- 每个任务应有稳定且唯一的编号、清晰结果、可检验的完成条件、依赖和状态；按项目规模补充优先级、主要落点、风险及验证方式。将大任务拆到能独立实施和验证的粒度，列明前置依赖，避免循环依赖和重复范围。
- 默认新任务使用原生 Markdown 任务列表：`- [ ]` 或 `- [x]`，状态与复选框在同一项，具体格式见模板。只在已满足所有适用验收条件、证据完整且状态为“已完成”时勾选；其他状态包括已取消均不勾选。手动修改复选框不能替代验收证据。
- 现有任务若有不同状态语义或格式，保留并遵循已有规范；不要自动重写旧任务或引入第二份状态来源。若用户明确要求给现有任务增加复选框，先核对状态和证据，保持历史、编号与语义，仅在授权范围内转换；缺少证据或状态冲突时说明并请用户确认，不擅自标完成。
- 任务编号一经分配不复用、不因重命名改变；拆分、合并、取消或阻塞保留历史及原因。关联其他任务集时链接其权威任务和证据，不复制出独立状态。创建任务集不等于开始实现，默认新任务为待开始；已实现的事项仅按可核实证据标记，文档整理完成不意味着产品交付完成。
- 给每个任务集一个明确的状态事实来源（默认 `tasks.md`）。`progress.md` 只汇总事实来源，`verification.md` 记录证据，不建立相互独立的状态副本。规模小时可裁剪章节，但不要丢失状态、验收条件和证据；已有项目约定的文件结构优先。

## 3. 维护和验收

阅读 `references/maintenance-and-verification.md`，按用户授权更新相关状态、进度与验证记录。区分实现完成和验收完成，记录实际执行的命令、日期、环境、结果与限制；跳过、未执行或阻塞不等于通过。用户手测和自动化分别留证，不推断未覆盖场景；不得保存秘密或未授权的私人内容。

真实数据变更、生产迁移、外部账号操作及破坏性验证须先确认环境、影响、备份／回退和授权。仅创建任务文档不授权执行这些操作。

## 4. 交付前检查

1. 对照来源和用户目标检查范围、非目标、假设、待确认项与跨任务集归属；检查编号唯一、依赖存在且无循环。
2. 检查复选框和状态一致，完成项有对应的验收证据；检查进度统计、取消任务口径、验证矩阵与事实来源一致。已有不一致或无法安全修复之处单独报告，不擅自更改历史。
3. 检查新增或修改的相对链接、文件路径及适用的仓库文档检查；只报告实际检查结果，不虚构测试或实测。
4. 简述修改的文件、推荐的下一项、待确认事项、执行过的检查以及未覆盖的验证。
