# mise 工具链与任务规范

让目标项目的工具版本、环境和任务可理解、可重复执行，同时保留现有工作。此 Skill 可用于单语言项目，不要求使用 Bun、uv 或 monorepo。

## 参考文件

路径相对本 Skill 目录，移植时携带整个目录：

- 版本、锁文件与环境示例：`references/configuration.md`。
- 任务设计、诊断和验证：`references/tasks-and-diagnostics.md`。
- 场景测试：`evals/evals.json`。

## 1. 确认现状和边界

1. 确认目标目录，阅读适用的 `AGENTS.md`、Git 状态、mise 配置、相关脚本、锁文件、CI 与容器配置。注意嵌套配置、当前工作目录及现有用户修改；不要直接覆盖。
2. 识别工具版本的现有来源、目标平台和实际任务；只修改用户要求范围。已有 asdf、系统包管理器或其他方案时，未经请求不要迁移或移除。
3. 不熟悉的项目配置可能执行代码或改变环境：先阅读配置及任务，再决定是否运行 `mise install`、`mise exec`、`mise run` 或信任操作；不要绕过信任机制。
4. 按实际 mise 版本查官方文档；可用时使用 Context7。滚动文档中的新功能须验证目标版本支持，不能把示例版本当默认值。

## 2. 管理版本、环境与锁文件

- 在项目配置中声明项目所需工具；根据已有策略或用户需求选择精确版本，并与其他清单中的工具版本核对。不要无关升级。
- `mise.lock` 锁定工具解析，不是应用依赖锁文件的替代品。是否生成、提交和使用锁定安装依目标版本、后端、平台与仓库规则决定；让工具生成，不手写校验和。
- 环境变量只承载所需配置：公开默认值与秘密分离，秘密由本地忽略文件或环境注入，不写入提交内容、日志或示例。确认配置来源和优先级，避免输出敏感值。
- 涉及 Python + uv 时先确认解释器的所有者。若明确采用 mise 提供 Python、uv 管理环境的方案，参考 `references/configuration.md`；不要另外启用会创建或激活第二套环境的机制。
- 工具安装、缓存、虚拟环境和模型数据是否放在项目内由目标项目决定；不要把本 Skill 示例中的路径或当前机器的路径强加给其他仓库。

## 3. 设计任务与变更

- 复用项目已有入口。安装、显式修改的格式化、只检查的格式/Lint/测试、诊断等职责应明确；聚合任务只调用实际存在的检查，失败应向上传递。
- 不能只凭任务名判断无副作用：检查实际子命令是否更新锁文件、同步环境、格式化、写产物或访问外部服务。区分源码/锁文件只读与可能写缓存或虚拟环境的执行。
- 本地、CI、容器可复用同一任务契约；缓存和虚拟环境要考虑平台与架构，不要承诺未经验证的平台可用。
- 初次生成、依赖/工具升级和日常锁定安装是不同操作。生成或更新锁文件只在任务要求的范围内执行；CI 检查失败不应自动改锁掩盖问题。

## 4. 验证与交付

根据变更范围运行项目已有的安装、检查和诊断任务；先检查命令的副作用和外部依赖。检查实际工具版本、配置和锁文件差异，验证失败传播，并检查未授权文件是否发生改变。避免输出 `.env` 内容。网络、平台或服务不可用时说明阻塞，不宣称验证通过。

报告修改的配置、版本/任务职责、执行的命令与结果、未验证项及潜在副作用。跨工具问题可将 `uv-standards` 作为补充参考；创建完整 mise + Bun + uv 仓库时，可选用 `monorepo-bootstrap`。这两个 Skill 未安装时，继续依据本 Skill 的配置参考、目标项目现状和对应工具官方文档完成本范围工作；不要因此重新初始化仓库。
