# 本地、CI 与开发容器

此处路径均相对目标仓库根目录。根据用户需求生成对应配置，不为了完整性预建部署环境。

## 共享执行入口

本地、CI 与容器统一使用根 `mise.toml` 的工具与任务：

```bash
mise install
mise run install
mise run check
mise run doctor
```

非交互进程不依赖 `mise activate` 或 `source .venv/bin/activate`。直接运行工具时使用 `mise exec -- ...`。

## 环境变量

- 公共、非敏感默认值可放根 mise 配置；本机差异放已忽略的本地配置或由宿主机注入。
- `.env.example` 只包含变量名称、用途与占位值；实际加载方式按选定工具版本配置并验证。
- 只有确有开发/测试/生产差异时才引入命名环境；环境差异不应产生互不一致的工具版本副本。
- 默认检查使用离线测试替身，不隐式调用真实付费服务。依赖首次下载与业务联网测试是不同事项。

## CI

1. 根据用户使用的平台创建 workflow，安装已验证版本的 mise。
2. 调用共享安装和检查任务，不复制一套漂移的 Bun/Python/uv 版本。
3. 冻结安装失败时直接失败，不能在 CI 中重新生成锁文件掩盖差异。
4. 缓存键考虑操作系统、架构、工具版本和锁文件摘要。优先缓存下载数据；跨平台不复用 `.venv/` 或 `node_modules/`。
5. 平台矩阵来自实际支持目标；未执行的平台不报告验证通过。

使用 CI 平台 Action（工作流组件）时查阅其官方文档并固定可追溯版本；不凭记忆生成过期配置。

## 开发容器

- `.devcontainer/` 镜像提供 mise 与必要系统依赖，容器创建后复用 `mise install` 和 `mise run install`。
- 使用容器内的依赖环境，避免把宿主机 `.venv/`、`node_modules/` 或平台构建产物直接用于 Linux 容器。工作区绑定挂载时，用容器 volume 等方式隔离这些路径。
- 安装完成不等于测试通过；在容器内另行执行检查并记录结果。
- 测试输入可只读挂载；项目状态和输出挂载到明确的可写目录。
- 容器配置不绑定作者机器的绝对路径；凭证在运行时注入，镜像不包含用户数据或凭证。

## 可复现性的交付范围

精确工具版本与锁文件解决工具及依赖解析的一致性，不自动保证系统库、硬件驱动和外部资源一致。仅在项目确实依赖这些内容时，补充系统依赖、供给方式及验证记录。
