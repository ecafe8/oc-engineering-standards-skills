# uv 项目与 workspace 规范

维护可复现的 Python 依赖和明确的解释器所有权。既支持单个 uv 项目，也支持多成员 workspace；不要求目标项目使用 mise 或 Bun。

## 参考文件

路径相对本 Skill 目录，移植时携带整个目录：

- 成员、依赖、锁定和执行示例：`references/workspaces.md`。
- 解释器、环境、排障与验证：`references/environments.md`。
- 场景测试：`evals/evals.json`。

## 1. 调查目标项目

1. 确认目标目录、适用的 `AGENTS.md`、Git 状态、根及成员 `pyproject.toml`、`uv.lock`、Python 版本来源、现有环境和相关任务。保留用户修改。
2. 识别项目是单项目、workspace 还是独立项目集合；检查现有成员匹配范围、发布需求、平台和 Python 兼容约束。不要因为看到多个目录就强行合并 workspace。
3. 确认谁安装 Python、谁管理虚拟环境；同时检查 `UV_PYTHON`、`UV_PROJECT_ENVIRONMENT` 等实际配置。用户没有要求时，不从 Poetry、pip 或现有方案迁移。
4. 用目标 uv 版本核对官方文档；可用时使用 Context7。网络或缓存不可用时报告限制，不编造锁文件或验证结果。

## 2. 管理成员和依赖

- workspace 各成员拥有自己的 `pyproject.toml`，共享 workspace 根锁文件。维护目标项目现有环境布局，不在成员内重复创建虚拟环境或锁文件来规避冲突。
- 依赖声明在实际使用的成员，区分运行时依赖和开发依赖组。包的发行名、Python 导入名和目录路径可能不同；命令参数按实际含义选择。
- 内部 workspace 依赖需要依赖声明和正确的 workspace source；验证安装后的真实导入，不用修改 `PYTHONPATH` 掩盖打包问题。示例见 `references/workspaces.md`。
- 可安装成员按目标项目约定配置构建后端和包发现；新增 `src/` 布局时验证其可安装性。根项目是否可打包由项目需求决定，不强加固定目录名。
- 多成员共享解析约束与兼容范围；冲突时检查版本与平台标记。确实无法共同解析时说明取舍，先与用户确认是否拆成独立项目。

## 3. 区分解析、同步和检查

- 首次创建及有意依赖变更可以更新锁文件；日常安装和 CI 使用目标项目的锁定策略。`--locked` 检查锁文件是否需要更新，`--frozen` 跳过一致性检查，不能用后者掩盖不匹配。
- `uv lock` 面向整个 workspace；根项目的默认同步/运行范围不一定包括全部成员，按需求明确使用 `--all-packages` 或 `--package`，并确认实际选项适用于目标版本。
- `uv run` 默认可能触发锁定和同步；即使使用 `--locked`，仍可能写入虚拟环境或缓存。若用户要求源码和锁文件只读，要选用适当选项并比较文件差异，不把它误称为完全无副作用。
- 不自动删除或重建已有环境；需要重建时先确认路径、可再生性和用户授权。需要迁移、升级或访问真实外部服务时，同样明确范围。

## 4. 验证与交付

检查清单、根锁文件与预期成员范围；按项目约定运行锁一致性检查、锁定同步、目标成员导入和真实测试。对只读要求比较运行前后源码及锁文件变化，并分别说明环境或缓存写入。只报告实际命令与结果；依赖下载、平台、模型等阻塞要明确列出。

报告变更成员、依赖与环境所有权、锁文件变化、测试和未验证事项。工具版本及统一任务可将 `mise-standards` 作为补充参考；完整多语言仓库初始化可选用 `monorepo-bootstrap`。这些 Skill 未安装时，依据本 Skill 的环境参考、目标项目现状和 uv 官方文档继续完成 Python 依赖与环境工作，不把跨 Skill 引用当作前置条件。
